## 1. Архитектура выполнения

### 1.1 Последовательность загрузки (`src/main.cpp`, `app_main`)
1. `sys_log_init()` – перенаправление логов ESP в кольцевой буфер RAM (отдается по HTTP).
2. `nvs_flash_init()`.
3. **Инициализация панели на ядре 1** (`display_init_task`) – см. раздел 1.3. Создает шину SPI2, панельный ввод-вывод (panel IO), панель AXS15231B и порт LVGL; запускает задачу LVGL (закрепленную за ядром 1).
4. `init_touch()` – создание устройства ввода тачскрина.
5. `show_splash_screen()` / `update_progress()` – ранняя заставка (встроенный шрифт).
6. `ui_loader_init()` – монтирование LittleFS, загрузка `settings.json` + `config.json` (запись значений по умолчанию при первом запуске).
7. `boot_guard_check()` – защита от циклической перезагрузки (принудительный переход в режим Wi-Fi AP после 3 быстрых перезагрузок).
8. `init_fonts()`, `i18n_init()`, `system_info_init()`, ресурсы заставки.
9. `init_keyboard(ble_enabled)` – BLE HID + задача вывода `kb_out`.
10. `macro_player_init()`, `obs_client_init()`.
11. Wi-Fi (`wifi_manager_*`) запускается только если `settings.wifi_enabled`.
12. `sd_card_init()` – монтирование `/sdcard` (не является фатальным при отсутствии карты).
13. `create_ui()` / `create_settings_page()` / `init_gestures()` / `set_brightness()` выполняются под блокировкой (lock) LVGL.
14. Наложение панели статуса.
15. Закрытие заставки; запуск `app_loop` (не закреплен за ядром) и `heartbeat` (ядро 0).

### 1.2 Задачи, ядра и приоритеты
Измерено через `uxTaskGetNumberOfTasks()` ≈ 14–17 задач (остальные – внутренние задачи IDF: `main`, `IDLE0/1`, `esp_timer`, `Tmr Svc`, `ipc0/1` и задачи стека Bluedroid).

| Задача | Создается в | Ядро | Приоритет | Стек | Назначение |
| :--- | :--- | :---: | :---: | :--- | :--- |
| **LVGL task** | `lv_port.c:118` | **1** (`task_affinity=1`) | 4 | 8192 | Цикл `lv_timer_handler`; владеет мьютексом LVGL; выполняет отрисовку (flush) + чтение тача |
| **display_init** | `main.cpp` | **1** | 5 | 8192 | Однократная инициализация панели (привязывает ISR SPI2 к ядру 1), затем удаляет себя |
| **Tear task** | `esp_bsp.c` | не закреплено (-1) | 4 | 2048 | Перезарядка семафора синхронизации TE для покадровой отрисовки без разрывов |
| **heartbeat** | `main.cpp` | **0** | 1 | 3072 | Диагностика каждые 5 с + сторожевой таймер зависаний (см. раздел 6) |
| **app_loop** | `main.cpp` | не закреплено | 3 | 4096 | Опрос клавиатуры, таймаут сна, подтверждение отката OTA |
| **macro_player** | `macro_player.c` | не закреплено | 4 | 4096 | Выполнение queued-шагов макросов |
| **obs_client** | `obs_client.c` | **0** | 4 | 6144 | Рабочий процесс OBS WebSocket (сокеты lwIP) |
| **kb_out** | `keyboard_manager.cpp`| не закреплено | 4 | 4096 | Сериализованный вывод HID (горячие клавиши/текст) |
| **wifi_req** | `wifi_manager.c` | не закреплено | 4 | 4096 | Вынос тяжелых операций Wi-Fi из задачи LVGL |
| **httpd** | `web_server.cpp` | **0** (`core_id=0`) | по умолч. | 6144 | `esp_http_server` |
| **Bluedroid / BT** | IDF | **0** | высокий | IDF | Контроллер BLE + хост |

**Почему именно такое распределение:**
* **Ядро 1 = UI + панель.** Отрисовка полного кадра ресурсоемка; удаление её из-под влияния стека радио/сети предотвращает голодание задач и срабатывание сторожевого таймера прерываний.
* **Ядро 0 = радио/сеть.** Bluedroid, задача Wi-Fi и `httpd` закреплены или создаются на ядре 0 (`CONFIG_BT_*_PINNED_TO_CORE_0=y`, `CONFIG_ESP_WIFI_TASK_PINNED_TO_CORE_0=y`, `http_cfg.core_id = 0`).
* Задача `heartbeat` работает на ядре 0 с приоритетом 1, поэтому она никогда не может вызвать голодание UI, но при этом сообщает о работоспособности системы, даже если задача UI заблокирована.
* **Стеки задач размещаются во внутренней RAM.** Не увеличивайте их без необходимости; внутренняя RAM является дефицитным ресурсом на этой плате (см. раздел 2.3).

### 1.3 Размещение прерываний / драйверов — САМОЕ ВАЖНОЕ ПРАВИЛО
Функция `spi_bus_initialize()` привязывает прерывание SPI2 к тому ядру, которое её вызвало. Панель AXS15231B находится на SPI2, а радиомодуль работает на ядре 0. Следовательно, панель **должна инициализироваться из задачи на ядре 1**:

```c
/* main.cpp */
xTaskCreatePinnedToCore(display_init_task, "display_init", 8192, NULL, 5, NULL, 1);
```

**Обоснование:** Если панель инициализировать из `app_main` (ядро 0), обработчик прерываний (ISR) SPI2 окажется на ядре 0 рядом с Bluedroid. Под нагрузкой Bluetooth передача цвета по QSPI может зависнуть; тогда SPI-транспорт `esp_lcd` будет бесконечно ждать завершения (`spi_device_get_trans_result(..., portMAX_DELAY)`), задача LVGL заблокируется, удерживая мьютекс LVGL, и весь интерфейс зависнет (экран погаснет, тач не реагирует). Перенос ISR на ядро 1 устранил воспроизводимое зависание; **не отменяйте это**.

**Подтверждающие факты (IDF 5.3.1):**
* `CONFIG_SPI_MASTER_ISR_IN_IRAM=y` (уже включено) гарантирует выполнение ISR SPI во время операций с flash/кэшем.
* `CONFIG_BT_BLUEDROID_PINNED_TO_CORE_0=y`, `CONFIG_BT_CTRL_PINNED_TO_CORE_0=y`.

### 1.4 Конвейер отрисовки
* **Интерфейс:** AXS15231B через QSPI (`use_qspi_interface = 1`), 40 МГц, RGB565, `LCD_RGB_ELEMENT_ORDER_RGB`, `quad_mode`.
* **Только полная перерисовка (Full refresh).** Путь QSPI отправляет только `CASET` (без `RASET`) и потоково передает кадр последовательно как `0x2C` / `0x3C` ("write continue"). Произвольные частичные прямоугольники **не адресуются**, поэтому драйвер дисплея работает с `full_refresh = 1`. Не включайте частичную перерисовку, пока в драйвер панели не будет добавлена адресация по окнам.
* **Поворот выполняется программно.** `LCD_ROTATION_DEG = 90`; MADCTL панели может выполнять зеркалирование (180°), но не может менять оси местами, поэтому `lvgl_port_flush_callback()` выполняет транспонирование+переворот в транспортный буфер перед вызовом `esp_lcd_panel_draw_bitmap()`.
* **Буфер кадра (`buf1`):** один полный кадр (320×480 пикселей = 307 КБ) в PSRAM, с одним буфером (`lv_disp_draw_buf_init(..., buf1, NULL, size)`).
* **Транспортные буферы (`trans_buf_1/2`):** `trans_size = 320*20 = 6400` пикселей (12 800 байт каждый) во внутренней DMA RAM. Таким образом, кадр отправляется 24 тайлами по 20 исходных строк; `max_transfer_sz = 320*20*2 = 12 800` байт.
* **Синхронизация TE (Tear Effect):** `bsp_display_sync_cb` ожидает фронт TE на GPIO38 (таймаут 15 мс) для первого тайла кадра; задача `Tear task` перезаряжает семафор.
* **Сериализация отрисовки (не удалять):** перед каждым вызовом `esp_lcd_panel_draw_bitmap()` процедура отрисовки ожидает на семафоре `trans_done_sem`, который освобождается callback-ом завершения передачи цвета по SPI. При таймауте она прерывает отрисовку кадра вместо вызова `draw_bitmap()`. **Обоснование:** SPI-транспорт `esp_lcd` повторно использует незавершенные транзакции с `portMAX_DELAY`, поэтому его вызов во время ожидающей передачи может навсегда повесить задачу LVGL. Пропуск кадра безвреден; зависание – фатально.

### 1.5 Параллелизм и правила блокировок
* Доступ ко всем объектам LVGL должен осуществляться под мьютексом LVGL: `bsp_display_lock(timeout_ms)` / `bsp_display_unlock()` (рекурсивный, обертка над `lvgl_port_lock`). Задача LVGL блокирует его внутренне.
* **Никогда не захватывайте блокировку LVGL с `timeout_ms = 0` (=`portMAX_DELAY`) из задачи, не являющейся задачей LVGL.** Используйте ограниченный таймаут и пропускайте обновление при неудаче (`connection_changed` использует 100 мс, `toast_show` использует 50 мс). Неограниченная межзадачная блокировка – это гарантированный deadlock.
* Вывод HID ставится в очередь (задача `kb_out`); `send_hotkey()` / `send_text()` возвращают управление немедленно, поэтому блокирующий вызов BLE никогда не заморозит UI.
* Тяжелые операции запуска/остановки Wi-Fi отправляются в задачи `wifi_req` / `wifi_cmd`, а не выполняются встроенно в обработчике событий LVGL.
* Опрос тача выполняется внутри задачи LVGL (callback indev), но через транспорт I2C с ограниченным таймаутом (см. 1.6).

### 1.6 Ввод с тачскрина (I2C)
* Тач AXS15231B @ адрес `0x3B`, 400 кГц, порт I2C 0, SDA GPIO4 / SCL GPIO8.
* Используется драйвер вендора, но его транспорт перенаправлен на "сырой" `i2c_master_dev_handle_t` с таймаутом 50 мс (`esp_lcd_touch_axs15231b_set_i2c_device()`, `esp_lcd_axs15231b.c`). Транспорт `esp_lcd_panel_io_i2c` от IDF выполняет каждую транзакцию с параметром `-1` (ждать вечно); поскольку тач опрашивается из задачи LVGL, один сбой передачи навсегда заморозил бы UI. Использование "сырого" устройства заставляет зависшую шину вернуть ошибку вместо бесконечного ожидания.
* После 3 последовательных ошибок чтения процедура отрисовки вызывает `bsp_i2c_recover()` (`i2c_master_bus_reset()`), а шина I2C использует новый драйвер `i2c_master` (а не устаревший `driver/i2c`) по той же причине (ограниченное время, легковесные прерывания).
* *Примечание:* IDF предупреждает об отсутствии подтягивающих резисторов I2C; на плате внутренние подтяжки не включены (`enable_internal_pullup = false`).
* **Дебаунс отпускания** (`lv_port.c`, `lvgl_port_touchpad_read`): панель может выдавать короткие «UP»-всплески, пока палец всё ещё удерживается (нестабильный контакт). Нажатие принимается сразу, а отпускание — только после `TOUCH_RELEASE_DEBOUNCE_READS` (4) подряд идущих чтений «UP». Без этого удержание пальца даёт фантомный `CLICKED` посреди нажатия (см. 1.9).

### 1.7 Модель работы радио
Одновременно работает только один радиомодуль (`radio_mode_t` в `config.h`):

| Режим | Enum | Что работает |
| :--- | :--- | :--- |
| BLE | `RADIO_MODE_BLE` | Только BLE HID, сеть отключена |
| AP | `RADIO_MODE_AP` | Wi-Fi AP + веб-конфигуратор (`ModiPAD_Setup` / `12345678`) |
| STA | `RADIO_MODE_STA` | Wi-Fi клиент, используется для подключения к OBS Studio |

**Обоснование:** BLE и Wi-Fi являются взаимоисключающими, так как они разделяют дефицитную внутреннюю RAM; демонтаж одного стека во время выполнения приводит к повреждению памяти. Переключение применяется путем сохранения настроек + перезагрузки (задача `radio_reboot` в `settings_page.cpp`). `settings.radio_mode` является единственным источником истины; `wifi_enabled` / `ble_enabled` вычисляются при загрузке (`ui_loader.c`). Веб-сервер запускается только в режиме Wi-Fi; `obs_client` подключается только в режиме STA (`wifi_manager_mode() == WIFI_APP_STA && wifi_manager_connected()`).

### 1.8 Статус-бар: вывод FPS / CPU

Верхний бар может показывать `FPS n` и `CPU n%` двумя метками с отступом 5 px по центру; включается в **Настройки → Общие → «Показывать FPS / CPU»** (`settings.json` `show_stats`, по умолчанию выключено). Значения обновляются раз в секунду и нормируются по реально прошедшему времени (`src/status_bar.cpp`, `src/lv_port.c`):

* **FPS** — кадры, отрисованные с прошлого тика (`lvgl_port_frame_count()`; при `full_refresh` один завершённый flush = один полный кадр).
* **CPU** — доля цикла задачи LVGL, проведённая внутри `lv_timer_handler()`: `100 * delta_busy_us / delta_total_us`.

Это **честные** числа: на статичном экране это ~0–1 FPS и единицы % CPU. Прежние значения (~10 FPS / ~40 % CPU) давал встроенный perf-монитор LVGL, который перерисовывал свою метку каждые **300 мс**, а на `full_refresh`-панели это **полный кадр 3 раза в секунду** — то есть он во многом измерял и создавал нагрузку сам. Встроенный монитор отключён (`LV_USE_PERF_MONITOR 0`); вывод в статус-баре рисуется раз в секунду, а при выключении вообще не вызывает периодических перерисовок.

### 1.9 Жесты, случайные нажатия и повторные срабатывания

Свайпы определяет сам LVGL (`LV_EVENT_GESTURE` приходит на экран; статус-бар, страницы и кнопки несут `LV_OBJ_FLAG_GESTURE_BUBBLE`, поэтому свайп распознаётся, даже если начался на статус-баре или кнопке). При этом LVGL также шлёт `CLICKED` кнопке под пальцем, если свайп начался на ней. Чтобы этого не происходило, `gesture_handler.cpp` запоминает время последнего жеста, а `gesture_swallow_click()` заставляет обработчик кнопок (`ui_renderer.cpp`) игнорировать клик, пришедший в течение `GESTURE_CLICK_GUARD_MS` (700 мс) после жеста.

**Повторные срабатывания.** Одно касание не должно вызывать два действия. Проблема была такой: удерживаем кнопку-переход → страница переключается → срабатывает ещё и кнопка, оказавшаяся под тем же пальцем на новой странице (либо удержание в итоге нажимает кнопку новой страницы). От этого защищают три независимых механизма; сохраняйте все:

1. **Блокировка переноса нажатия — `LV_OBJ_FLAG_PRESS_LOCK`.** Пока указатель нажат, `lv_indev.c` (`indev_proc_press`) **на каждом цикле** заново ищет объект под точкой и, если он сменился, шлёт старому `PRESS_LOST`, а новому `PRESSED`. После программного переключения страницы этим объектом становится кнопка на том же месте новой страницы. Каждая кнопка в `ui_renderer.cpp` получает `LV_OBJ_FLAG_PRESS_LOCK`, поэтому повторный поиск пропускается и нажатие остаётся привязанным к исходной кнопке.
2. **Палец обязан оторваться — input gate (`gesture_handler.cpp`).** Когда срабатывает действие кнопки или происходит переключение страницы (`ui_show_page()`), `input_gate_arm()` выставляет флаг **и** вызывает `lv_indev_wait_release()`. LVGL отменяет текущее нажатие (без `CLICKED` на отпускании) и игнорирует новые нажатия, пока указатель не будет отпущен. `input_gate_filter()` в колбэке чтения тача форсирует `RELEASED`, пока gate взведён, и снимает его только после того, как состояние «отпущено» продержится два чтения. Итог: **одно действие на одно физическое касание** — следующей кнопке нужен новый тап.
3. **Дебаунс отпускания (см. 1.6).** Не даёт коротким «UP»-всплескам панели открыть gate раньше времени посреди удержания.

В результате долгое удержание кнопки-перехода переключает страницу ровно один раз и никогда не нажимает кнопку, оказавшуюся под пальцем; для следующего действия нужно отпустить палец и нажать снова.

Если нажатия всё ещё срабатывают ложно: увеличьте `GESTURE_CLICK_GUARD_MS`, поднимите `TOUCH_RELEASE_DEBOUNCE_READS` или поднимите `gesture_limit` / `scroll_limit` LVGL (в init indev), чтобы для свайпа требовалось больше движения.

## 2. Модель памяти

### 2.1 Физическая память
| Область | Размер | Скорость | Примечания |
| :--- | :--- | :--- | :--- |
| **Внутренняя SRAM (DRAM/IRAM)** | 512 КБ | 240 МГц | **Дефицитна** – стеки, буферы DMA, стеки радио, ISR |
| **PSRAM** | 8 МБ octal | 80 МГц, ECC | Только большие буферы; **не поддерживает DMA для SPI** |
| **Flash** | 16 МБ | QIO 80 МГц | код + LittleFS |
| **microSD** | зависит от карты | 1-bit SDMMC | Только объемные медиафайлы |

`esp_psram` сообщает ~7680 КБ доступной памяти из-за ECC; общий heap ≈ 7936 КБ.

### 2.2 Что и где размещается, и почему
| Выделение | Область | Обоснование |
| :--- | :--- | :--- |
| Буфер кадра LVGL (`buf1`) | **PSRAM** (`buff_spiram=true`) | Полный кадр 307 КБ не помещается во внутреннюю RAM |
| Транспортные буферы LVGL (`trans_buf_1/2`) | **Внутренняя DMA** (`MALLOC_CAP_DMA`) | QSPI DMA не может читать из PSRAM; буферы сделаны минимальными (2×12.8 КБ) |
| Кольцевой буфер системных логов | **PSRAM** (`MALLOC_CAP_SPIRAM`) | Жертвенный, относительно большой буфер |
| Строки путей к ресурсам | **PSRAM** (`ui_assets.cpp`) | Предотвращает фрагментацию внутренней RAM |
| Стеки задач | **Внутренняя** | Требование FreeRTOS |
| Стеки Wi-Fi + Bluedroid | **Внутренняя** | Требование IDF; главная причина, почему радио работают поочередно |
| Драйверы SPI/I2C, ISR | **Внутренняя/IRAM** | Аппаратное требование |

### 2.3 Бюджет внутренней RAM (наблюдаемый на этой плате)
| Момент замера | Свободно внутри | Largest internal block |
| :--- | :--- | :--- |
| После монтирования LittleFS | ~119 КБ | ~57 КБ |
| После запуска BLE HID | ~54 КБ | ~31 КБ |
| Устойчивое состояние (BLE, UI построен) | ~41 КБ (min ever) | **~31 КБ** |

**Последствия:** После запуска BLE остается всего ~31 КБ непрерывной внутренней RAM. Любое новое крупное выделение во внутренней/DMA памяти, увеличение стека задачи или буфера без поддержки PSRAM может сломать работу BLE/`httpd`/LVGL. Отдавайте предпочтение PSRAM; держите буферы DMA крошечными. Именно поэтому транспортные буферы имеют размер 12.8 КБ (помещаются 2 штуки) и почему радио работает в одно-режимном режиме.

## 3. Модель хранения данных

### 3.1 NVS
Минимальное использование. Только пространство имен `boot` хранит счетчик циклических перезагрузок (см. `boot_guard_check` в `main.cpp`). Настройки в NVS не хранятся.

### 3.2 LittleFS (`/littlefs`, диск LVGL `S:`)
Раздел `storage` @ `0x820000`, размер `0x7E0000` (~7.9 МБ). Прошивается из папки `datadevice/` командой `pio run -t uploadfs`.
| Файл / директория | Содержимое |
| :--- | :--- |
| `config.json` | Схема UI v3 (заголовок настроек, `main_page`, `pages[]`) |
| `settings.json` | Настройки времени выполнения (см. раздел [Интерфейс](interface_rus.md) 1) |
| `fonts/` | `roboto_{10,12,14,16,18}[_bold].bin` (ASCII + кириллица, bpp 4) |
| `web/` | `index.html`, `style.css`, `app.js`, `locales/{ru,en}.json` |
| `images/` | Библиотека PNG по умолчанию (см. раздел [Интерфейс](interface_rus.md) 3) |

### 3.3 microSD (`/sdcard`, диск LVGL `D:` = `/sdcard/modipad`)
SDMMC 1-bit, монтируется в `/sdcard`. Исходная папка в репозитории: `datasdcard/modipad` (развертывается скриптом `scripts\sync_sd.bat`).
| Путь | Содержимое |
| :--- | :--- |
| `/sdcard/modipad/backgrounds` | PNG-фоны страниц |
| `/sdcard/modipad/images` | Дополнительная библиотека изображений |
| `/sdcard/modipad/sounds` | Звуки нажатия кнопок |
| `/sdcard/modipad/config/backup_<version>_<n>.json`| Резервные копии конфигурации (`config_backup.c`; `<version>` = `MODIPAD_FIRMWARE_VERSION`, `<n>` = секунды uptime) |
| `/sdcard/update.bin` | Образ прошивки для OTA-обновления с SD |

### 3.4 Разрешение путей к ресурсам
Функция `asset_resolve_image()` (в `ui_assets.cpp`) сначала проверяет flash (`S:`), затем карту (`D:`). Таким образом, фон может находиться в любом из этих мест без редактирования `config.json`. Эмуляторы зеркально отражают это поведение (см. раздел 8).

### 3.5 OTA и откат (Rollback)
Таблица разделов поддерживает двойной OTA: `ota_0` @ `0x20000`, `ota_1` @ `0x420000`, плюс `otadata`. После 15 секунд успешной работы `app_loop` вызывает `esp_ota_mark_app_valid_cancel_rollback()`; в противном случае загрузчик откатит плохой образ (`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y`). Источники обновления: веб (`POST /api/ota`, `POST /api/ota/sd`) и файл `update.bin` на SD (Настройки → Система). См. `ota_update.c` / `web_server.cpp`. Функция `boot_guard_check()` принудительно включает режим Wi-Fi AP после 3 быстрых перезагрузок, чтобы неправильные настройки радио всегда можно было переконфигурировать.

## 6. Диагностика и настройка

### `MODIPAD_DIAG_STAGE` (`src/config.h`)
Переключатель прогрессивной изоляции на этапе сборки, используемый для проверки панели/драйвера:
| Значение | Конфигурация |
| :--- | :--- |
| **0** | **Продакшен** (всё включено, автосон включен) |
| 1 | Только UI (дисплей + тач + LVGL + heartbeat) |
| 2 | UI + макросы + рабочий процесс OBS (радио выключены) |
| 3 | Только UI + клавиатура/радио (макросы/OBS выключены) |
| 4 | Всё (эквивалентно 0) |

Автосон отключен для всех этапов, кроме 0. Полезно, когда будущее зависание требует изоляции между "UI/драйвером" и "сетевыми задачами".

### Heartbeat (`src/main.cpp`, `heartbeat_task`)
Задача на ядре 0 выводит каждые 5 секунд:
```text
HEARTBEAT: alive heap=.. int_min=.. int_largest=.. psram=.. tasks=.. locked=.. stage=.. loops=.. flush=.. done=.. exit=.. skip=.. uptime=..s
```
* `int_largest` – largest contiguous internal block (запас прочности для радио/LVGL).
* `loops` – счетчик живости задачи LVGL; он всегда увеличивается, если задача не заблокирована.
* `stage` – последнее место входа задачи LVGL (0 = idle, 10–19 = чтение тача, 20–29 = путь flush); `22` = ожидание завершения DMA, `23` = внутри `draw_bitmap`.
* `flush` / `done` / `exit` / `skip` – начатые отрисовки / завершения передачи цвета-DMA / завершенные отрисовки / кадры, прерванные из-за таймаута DMA.

**Сторожевой таймер зависаний (Stall watchdog):** если `loops` не увеличивается в течение ~10 с, задача действительно заблокирована, и устройство выполняет `esp_restart()` (`LVGL task stalled ... - rebooting to recover`). Это мера самовосстановления; здоровое устройство никогда не запускает его.

### Как проверить изменение
1. `pio run` (сборка), `pio run -t upload`.
2. Откройте монитор и следите за `HEARTBEAT`: `loops` должен постоянно расти, `skip` должен оставаться равным 0, `int_largest` не должен схлопываться, и не должно быть строк перезагрузки.
3. **Стресс-тест:** подключите хост BLE и прокручивайте Настройки → О системе и страницу с текстовыми полями в течение нескольких минут (самый тяжелый путь перерисовки).
4. Если происходит реальное зависание, вы увидите `stage=23` с замороженным `loops` и автоматической перезагрузкой – зафиксируйте лог до перезагрузки.

## 7. Критические инварианты (НЕ НАРУШАТЬ)

1. **Инициализируйте панель из ядра 1** (`display_init_task`). Никогда не вызывайте `init_display()` напрямую из `app_main`. Это удерживает ISR SPI2 вдали от ядра Bluedroid; нарушение этого правила возвращает жесткое зависание. (См. раздел 1.3.)
2. **Сохраняйте `full_refresh = 1`.** Драйвер QSPI адресует только полные кадры; не включайте частичную перерисовку, пока вы сначала не реализуете адресацию по окнам CASET/RASET в драйвере панели.
3. **Сохраняйте рукопожатие (handshake) отрисовки.** Никогда не вызывайте `esp_lcd_panel_draw_bitmap()` без ожидания (с таймаутом и прерыванием кадра при таймауте) предыдущей передачи цвета. SPI-транспорт `esp_lcd` повторно использует незавершенные передачи с `portMAX_DELAY`.
4. **Размещение в памяти:** буфер кадра LVGL в PSRAM; транспортные буферы во внутренней DMA RAM и небольшого размера; PSRAM не поддерживает SPI-DMA.
5. **Никогда не захватывайте блокировку LVGL без ограничений из задачи, не являющейся задачей LVGL** (`bsp_display_lock(0)` = бесконечность). Используйте ограниченный таймаут; при неудаче пропускайте действие.
6. **Держите BLE/Wi-Fi на ядре 0** и `CONFIG_SPI_MASTER_ISR_IN_IRAM=y`.
7. **Держите тач на ограниченном транспорте I2C** (50 мс) с функцией восстановления шины.
8. **Радиомодули остаются одно-режимными;** переключение осуществляется через сохранение + перезагрузку.
9. **Следите за внутренней RAM** (`int_largest` ≈ 31 КБ после запуска BLE). Отдавайте предпочтение PSRAM для всего крупного; не увеличивайте стеки задач/буферы DMA без измерений.
10. **Не меняйте без необходимости тактовую частоту/геометрию QSPI.** 40 МГц + тайлы по 20 строк отлажены; снижение до 20 МГц усугубило разрывы кадров (tearing) и не исправило зависания.
11. **Вывод горячих клавиш/текста проходит через очередь `kb_out`**, а не напрямую из обработчика событий LVGL.
12. **Держите `lv_conf.h` в `lib/lvgl/`** (не переключайтесь на управляемый компонент LVGL), если только вы не мигрируете код UI на LVGL v9.
13. **Сохраняйте защиту от повторных срабатываний:** `LV_OBJ_FLAG_PRESS_LOCK` на кнопках, `input_gate_arm()` / `lv_indev_wait_release()` при действиях и переключении страниц и дебаунс отпускания тача (`TOUCH_RELEASE_DEBOUNCE_READS`). Удаление любого из них возвращает двойное срабатывание (переход на страницу плюс нажатие кнопки на новой странице). (См. 1.6 / 1.9.)

## 8. Симулятор (ПК, SDL2)

`simulator/` – это **отдельный** проект PlatformIO, который отображает **реальные модули UI** (`ui_renderer`, `splash_screen`, `status_bar`, `settings_page`, `gesture_handler`, `ui_loader`, `ui_assets`) в окне SDL2 (или Win32), используя локальный LVGL 8.4 проекта и локальный `tools/sdl2/` (без загрузок во время сборки). Бэкенд дисплея/ввода реализован напрямую в `main_host.cpp` вместо `lv_drivers`, который недоступен в офлайн-режиме.

**Исходники UI компилируются напрямую из `../src`** (через `env.BuildSources()` в `extra_paths.py`) — копии `src/project/` больше **нет**. Под `simulator/src/` остаются только точка входа хоста, заглушки и cJSON, поэтому симулятор всегда отражает текущий код прошивки. `splash_screen.cpp` включает `esp_bsp.h`; этот заголовок компилируется на месте и имеет ветку `#ifdef HOST_BUILD`, предоставляющую только хелперы мьютекса LVGL.

```bash
start.bat                           :: главное меню: [10] SDL2, [11] Win32
simulator\run_simulator.bat         :: SDL2  (env native,      требует SDL2.dll)
simulator\run_win32_simulator.bat   :: Win32 (env native_win32, без DLL)
```

| env | точка входа | окно | зависимости |
| :--- | :--- | :--- | :--- |
| `native` | `src/main_host.cpp` | SDL2 | `SDL2.dll` рядом с exe |
| `native_win32` | `src/main_host_win32.cpp` | Win32/GDI | нет |

```text
simulator/
├── platformio.ini          # [env:native]
├── lv_conf.h               # Конфиг LVGL для ПК (COLOR_16_SWAP 0, MEM_CUSTOM 0)
├── extra_paths.py          # пути включения, дефайны, локальный SDL2, -Wl,--wrap=fopen
├── run_simulator.bat       # проверяет SDL2, синхронизирует, собирает, копирует SDL2.dll, запускает
├── sync_project.bat        # копирует datadevice/ + datasdcard/ в simulator/ (только данные)
├── src/
│   ├── main_host.cpp            # Окно SDL2 + flush + мышь/тач + свайп
│   ├── main_host_win32.cpp      # Бэкенд окна Win32/GDI (env native_win32)
│   ├── host_stubs.cpp           # "Аппаратные" заглушки + __wrap_fopen
│   ├── cjson/                   # cJSON (скопирован из локального пакета IDF)
│   └── compat/                  # поддельные заголовки esp_*/freertos/driver
├── datadevice/             # сгенерировано: копия ../datadevice (содержимое flash)
└── datasdcard/             # сгенерировано: копия ../datasdcard (содержимое SD)
```

`fopen` перенаправляется на этапе компоновки с помощью `-Wl,--wrap=fopen`: `__wrap_fopen` переписывает `/littlefs/...` в `./datadevice/...` и `/sdcard/...` в `./datasdcard/...`, поэтому реальные `ui_loader` / `ui_assets` и POSIX-драйвер FS LVGL читают фактическую конфигурацию и изображения без изменений в исходном коде. Аппаратные вызовы (`set_brightness`, `send_hotkey`, `init_keyboard`, `init_web_server`, мьютекс LVGL) заглушены в `host_stubs.cpp`. Навигация свайпами и нажатия кнопок управляются циклом событий SDL через публичные хелперы tabview.

**Примечания:**
* Исходники UI компилируются напрямую из `../src` (через `env.BuildSources()` в `extra_paths.py`); копии `src/project/` больше нет, поэтому симулятор всегда использует текущий код прошивки. `esp_bsp.h` имеет ветку `#ifdef HOST_BUILD`.
* `ui_loader` — это чистый C и в прошивке (`src/ui_loader.c`), т.к. хост-компилятор MinGW GCC 5.1 отвергает назначенные инициализаторы C99 в C++. Сохраняйте модули только на C совместимыми с C.
* SDL2 должен быть 32-битным (i686) пакетом dev в `tools/sdl2/`.
* `SIM_AUTOEXIT_MS=<ms>` запускается на несколько секунд, затем выходит (дымовой тест).
* **Требования:** Платформа `native` PlatformIO не включает компилятор:
  ```bash
  pio pkg install -g -t platformio/toolchain-gccmingw32
  ```
  `run_simulator.bat` добавляет его в `PATH`. Сборка основной прошивки (`pio run`) не затрагивается – эта папка является отдельным проектом PlatformIO, не связанным со сборкой ESP-IDF.

## 9. Антипаттерны (не повторять)

Ниже — ошибки, которые **реально были допущены и исправлены** в этом проекте. Прочитайте перед правками драйвера, пути flush, логирования, раскладки задач или `sdkconfig`.

| Жёсткое зависание UI при Bluetooth (экран тёмный, BLE подключён) | Прерывание SPI2 (QSPI-панель) было на **ядре 0** вместе с Bluedroid; передача QSPI встаёт, а `esp_lcd` ждёт вечно | Инициализировать панель из **задачи на ядре 1** (`display_init_task`) — см. 1.3 |

## 10. Рабочая конфигурация и лучшие практики

Приведённые ниже настройки и приёмы проверены на этой плате. Считайте их значением по умолчанию и отклоняйтесь только по результатам измерений.

**Ядра и задачи**
* Ядро 1: задача LVGL **и** инициализация панели (`display_init_task`).
* Ядро 0: Bluedroid, Wi-Fi, `httpd`, `obs_client` и низкоприоритетный `heartbeat` (приоритет 1).
* ISR панели (SPI2) — на ядре 1; `CONFIG_SPI_MASTER_ISR_IN_IRAM=y`.

**Память**
* Фреймбуфер LVGL — в **PSRAM**; транспортные буферы — маленькие, во **внутренней DMA** RAM; кольцевой лог и строки путей — в PSRAM.
* Внутренняя RAM — дефицитный ресурс (~31 КБ крупнейший блок после BLE) — не растите стеки/DMA-буферы без проверки heartbeat.

**Отрисовка**
* QSPI 40 МГц, тайлы 20 строк, `full_refresh = 1`, программный поворот 90°, синхронизация по TE на первом тайле, flush сериализован с ограниченными ожиданиями и отменой кадра при таймауте.

**Тач**
* Сырое устройство `i2c_master` (адрес `0x3B`, 400 кГц) с таймаутом 50 мс; восстановление шины после 3 ошибок подряд.

**Многопоточность**
* Весь доступ к LVGL — из задачи LVGL или под **ограниченным** `bsp_display_lock`; вывод HID — через очередь `kb_out`; тяжёлые Wi-Fi операции — в задачах `wifi_req`/`wifi_cmd`.

**Радио и хранение**
* Одно радио за раз; переключение через сохранить + перезагрузка. Dual-OTA + откат + защита от boot-loop. `config.json` (pages/language/obs/network) и `settings.json` (`AppSettings`) перезагружаются в RAM при web-POST.

**Логирование**
* По умолчанию уровень **INFO**; повышайте по тегам в рантайме (`esp_log_level_set`). Логи дублируются в PSRAM-кольцо, отдаваемое по `/api/log`. Никогда не включайте глобальный VERBOSE (USB-Serial-JTAG консоль блокируется без читателя).

**Диагностика**
* `MODIPAD_DIAG_STAGE` для изоляции; heartbeat печатает `loops` (живость), `flush/done/exit/skip` и `int_largest`; замерший `loops` вызывает авто-перезагрузку.

**Анимации**
* Отсутствуют. Переключение страниц мгновенное; snap tabview пропатчен на `LV_ANIM_OFF`, а запущенная анимация скролла отменяется перед переключением.

**Ресурсы и сборка**
* Имена файлов страниц ≤15 символов; `asset_resolve_image()` проверяет flash `S:`, затем SD `D:`. Эффективный конфиг сборки — `sdkconfig.modipad`.
* Симулятор компилирует **продакшн**-исходники напрямую (без копий), с веткой `HOST_BUILD` в `esp_bsp.h` и заглушками в `host_stubs.cpp`. Его `lv_conf.h` повторяет устройские `LV_GRAD_CACHE_DEF_SIZE`/`LV_DITHER_GRADIENT`, чтобы градиентные баги, видимые только на устройстве, воспроизводились на ПК.
* Патч вендорного LVGL: `lv_draw_sw_gradient.c` `compute_key()` хэширует **содержимое** градиента, а не указатель на дескриптор. Штатный ключ по указателю заставлял все градиенты одного размера (напр. все плитки главной и Multimedia) переиспользовать цвета первого градиента при `LV_GRAD_CACHE_DEF_SIZE != 0`.

**Версионирование**
* `MODIPAD_FIRMWARE_VERSION` в `src/config.h` — единственный источник истины (страница «О системе» и имена резервных копий на SD `backup_<version>_<n>.json`). Дублируйте его в `datadevice/web/app.js` (`APP_VERSION`) и в cache-buster `?v=`.
* `extra_script.py` (пост-сборка) складывает каждый собранный образ в `firmware/<version>/`, чтобы старые версии сохранялись для истории.

## 11. Распиновка и подключение

Вся плата — это модуль JC3248W535EN; единственный внешний разъём — слот microSD. Линии дисплея, тача и подсветки зафиксированы на модуле и описаны в `src/config.h`.

| Сигнал | GPIO | Сигнал | GPIO |
|--------|------|--------|------|
| CS     | 45   | DATA2  | 40   |
| PCLK   | 47   | DATA3  | 39   |
| DATA0  | 21   | DC     | 8 (не используется для QSPI) |
| DATA1  | 48   | TE     | 38   |
|        |      | BL     | 1    |

- **Дисплей (QSPI):** CS = GPIO45, PCLK = GPIO47, DATA0..3 = GPIO21/48/40/39, DC = GPIO8 (для QSPI не используется), TE = GPIO38.
- **Тачскрин (I2C):** SDA = GPIO4, SCL = GPIO8. Пины INT и RST тача отсутствуют (оба `-1`), внешние подтягивающие резисторы I2C не настроены; шина работает на 400 кГц на новом драйвере `i2c_master`.
- **Подсветка:** GPIO1 (яркость через PWM).
- **microSD (SDMMC 1-bit):** D0 = GPIO13, CLK = GPIO12, CMD = GPIO11 (внутренние подтягивающие резисторы).
- **USB:** нативный ESP32-S3 USB-Serial-JTAG (использует USB-разъём модуля, GPIO-пины не задействованы).

## 13. Устранение неполадок

### Экран зависает / гаснет и не просыпается
- Проверьте строку `HEARTBEAT`: замороженный `loops` + `stage=23` означает, что задача LVGL заблокирована при передаче на панель. Heartbeat автоматически перезагрузит устройство через ~10 с. Зафиксируйте лог.
- Убедитесь, что панель по-прежнему инициализируется с **ядра 1** (инвариант 1) и что рукопожатие flush (инвариант 3) не удалено.
- Растущий `skip` при растущем `loops` = кадры прерываются по таймауту DMA (UI жив, просто пропускает кадры). Обычно временное явление.

### Давление на внутреннюю RAM (`int_largest` мал / радио не запускается)
- Что-то крупное было выделено во внутренней RAM. Переместите это в PSRAM, уменьшите буферы DMA/стеки или освободите память. См. 2.3.

### Wi-Fi или BLE не запускаются после изменения
- Вероятно, истощение внутренней RAM из-за нового выделения. Проверьте `int_largest` в heartbeat непосредственно перед запуском радио.

### PSRAM медленно истощается при навигации
- Страницы строятся лениво и сохраняются в RAM (схема v3, `ui_renderer.cpp`). Каждая посещённая страница стоит PSRAM. Сейчас это сделано намеренно; освобождение скрытых страниц — возможная будущая оптимизация.

### Подробные логи после перезагрузки
- Флаг `-DLOG_LOCAL_LEVEL=ESP_LOG_VERBOSE` вместе с уровнем логов загрузчика даёт большой дамп при загрузке. Понизьте `LOG_LOCAL_LEVEL` (и, при необходимости, уровень загрузчика) для релизных сборок.

### Ничего на панели / неправильные цвета
- Проверьте `full_refresh = 1`, геометрию QSPI (`use_qspi_interface`), порядок элементов RGB и поворот. Не переключайтесь на частичную перерисовку.

### Примечания
- LittleFS предоставляется компонентом `joltwallet/littlefs` (объявлен в `src/idf_component.yml`); сборщик скачивает его автоматически.
- LVGL загружает изображения через POSIX-драйвер FS (`LV_USE_FS_POSIX`, буква `S`, базовый путь `/littlefs`); `LV_USE_FS_FATFS` отключён во избежание конфликта букв дисков.
- Раздел `storage` создаётся файлом `partitions/modipad_16MB.csv`.
- Этот проект — порт на ESP-IDF референса JC3248W535EN `DEMO_LVGL` (Arduino); сохраняйте файлы драйверов (`esp_lcd_axs15231b.[ch]`, `esp_lcd_touch.[ch]`) близкими к версии вендора и повторно применяйте два намеренных отклонения (транспорт I2C тача с ограниченным таймаутом, QSPI 40 МГц), если синхронизируете их заново.
